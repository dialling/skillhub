# 商品简介写法（SkillHub 标准）

> 这份文档定义商店里每一条简介必须满足什么。数据来自 `docs/research/corpus-own.md`
> 收集的逐字语料（中文 awesome-list、公众号长文、CSDN/腾讯云/阿里云清单、Taste-Skill
> 的英文表格，以及 Anthropic 官方 description 指南）。

## 为什么改

改写前的 60 条简介：**最短 35 字，中位 50，最长 89**，且 58/60 都含「技能/工具」这种自指词，
13/60 以「为…／面向…」开头。典型反例：

| 原文 | 问题 |
|---|---|
| `以智能体为中心的本地技能控制面，内置两千多个技能目录、CLI、本地 MCP 与工作台，便于检索选型与校验。` | 名词堆叠，读完不知道能干什么 |
| `Agent Skills 的官方规范与文档仓库，定义 SKILL.md 的结构、发现机制与最佳实践，是该生态的权威依据。` | 60 字在解释「它很重要」，不是「能干什么」 |
| `为跨平台界面设计注入设计智能的技能，帮助智能体产出更专业的 UI/UX 方案与前端实现。` | 「注入设计智能」是空话 |

这类写法在语料里被反复点名：`xlsx Skill专攻Excel/CSV文件`（同义反复）、
`pptx Skill是救场专用`（悬念式）、`PDF Skill集成了pypdf、pdfplumber、reportlab等库`（实现细节）、
`这是官方Skill里下载量排第一的`（榜单信息而非功能）。

## 公式

三种结构，按出现频率排序：

1. **`[动词] + [对象] + [产出/结果]`**
   `上传 CSV 自动生成统计摘要与可视化` · `为函数或模块自动生成单元测试`
2. **`让/把 + [对象] + [告别/变成] + [痛点]`**
   `让你生成的网页告别「AI 味儿」` · `把最枯燥的测试编写工作丢给 AI`
3. **`[输入] → [输出]`**
   `照片或一句话 → 极简纸感版面`

Anthropic 官方给的是同样的骨架，只是面向模型而非人：
`[What it does]. Use when [trigger phrases, contexts].`

## 硬性预算

| 指标 | 要求 | 改写前 | 改写后 |
|---|---|---|---|
| 字数 | **13–30**，中位约 20 | 中位 50 | **中位 20** |
| 最长 | ≤ 32 | 89 | **31** |
| 自指词（技能/工具/skill） | 仅在它真的是功能时使用 | 58/60 | 34/60 |
| 以「为…／面向…」开头 | 禁止 | 13/60 | 0 |
| 实现细节（库名、CLI、语言名） | 禁止 | 12/60 | 0 |

## 必须做的事

- **说产出，不说身份**。「这是个官方技能」不是功能，「让 AI 会读会写 PDF」才是。
- **动词开头**，或「让/把」开头。
- **一条只讲一件事**。Taste-Skill 的 README 把这条写成规矩：
  `Each skill does one job; you do not need all of them at once.`

## 反面清单

- ❌ 同义反复：`Excel Skill 专攻 Excel 文件`
- ❌ 悬念式：`pptx Skill 是救场专用`
- ❌ 榜单信息：`下载量排第一的`
- ❌ 实现细节：`集成了 pypdf、pdfplumber、reportlab`
- ❌ 出处身份：`Anthropic 官方仓库中的示例 Skill`
- ❌ 自指填充：`……的技能`、`……的工具`
- ❌ 万能触发器：`适用于任何与代码质量、测试、调试相关的工作`

## 落地

- 数据字段：`taglineZh` / `taglineEn`（卡片与详情页首屏）、`useWhen`（「什么时候用」）、
  `aboutZh`（原来的长简介，只在详情页「关于」里出现）。
- 生成脚本：`scripts/rewrite-catalog-blurbs.mjs`，改完会打印字数分布与自指计数，
  用来防止回退。
- 新增条目时照此写法补齐，脚本会拒绝未覆盖的仓库。
